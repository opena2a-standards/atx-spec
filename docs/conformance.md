# Conformance

Byte-stable conformance fixtures and SDK-independent reference verifiers for ATX v1.0 and v1.1 live at [`opena2a-standards/atx-conformance`](https://github.com/opena2a-standards/atx-conformance). The suite ships 41 fixtures — the v1.0 set (baseline valid, hybrid Ed25519 plus ML-DSA-65, that credential with its Ed25519 signature removed, leaving one ML-DSA-65 signature that verifies, which [`core.md`](../core.md) §13 rejects because an ML-DSA-65 entry needs a verifying Ed25519 entry beside it, three verifying signatures from one authority's threshold key set, which pin that each signature verifies and not the threshold of [`core.md`](../core.md) §1.3 step 5, that credential cut to one of its three signatures, the primary's, under a verifier state that holds the authority's three Ed25519 keys and requires two of them, which [`core.md`](../core.md) §1.3 step 5 rejects because the signatures that verify fall short of the threshold and a verifier that checks only that every declared signature verifies wrongly accepts, revoked, revoked on list membership alone with the credential's own `revoked` flag false, expired, wrong-issuer, cross-issuer-key, tampered-signature, malformed-schema) plus the `v1_1-*` family (JCS-form baselines, signed-field integrity via tampered `capabilities`, issuer binding, an untrusted chain authority that contributes no eligible key even when named in the signed `issuerChain`, `declaredPurpose` carried under the signature, the §1.3a.2 rule-5 degenerate inputs — whitespace-empty object accepted as absent, injected array/string/number values rejected — and strict credential parse: duplicate object members rejected at any depth per RFC 8259 §4, case-variant members that a last-wins JSON decoder would collapse rejected as `PARSE_ERROR`, and a member added after signing whose name is that of a member the credential carries with its `i` replaced by a letter outside ASCII, `ıssuedAt` (U+0131 LATIN SMALL LETTER DOTLESS I) beside `issuedAt` in one credential and `İd` (U+0130 LATIN CAPITAL LETTER I WITH DOT ABOVE) beside `id` in another, which [`core.md`](../core.md) §1.3a.2, naming every member a v1.1 credential may hold, rejects as `PARSE_ERROR` and a verifier that ignores a member it does not know wrongly accepts, and a hybrid credential whose ML-DSA-65 signature is forged while its Ed25519 signature stays intact, which every declared signature having to verify rejects, a hybrid credential carrying one ML-DSA-65 signature that verifies and no Ed25519 signature, which `core.md` §13 rejects because an ML-DSA-65 entry needs a verifying Ed25519 entry beside it, a credential omitting the optional `transparencyLogIndex`, which a verifier that still requires the field wrongly rejects, a credential signed with `scanSummary.criticalFindings` 0 that carries the JSON string `"3"` in that member, written after signing, which [`core.md`](../core.md) §1.3a.2 rule 2 makes a signature failure and a verifier that leaves a member it cannot decode at its zero value wrongly accepts, a credential carrying `scanSummary.criticalFindings` 9007199254740993 under a signature over the bytes an RFC 8785 serializer that reads each number as an IEEE 754 double writes for it, with 9007199254740992 in that member, which [`core.md`](../core.md) §1.3a.2 rule 3 makes a signature failure because the value is above 9007199254740991 (2^53 - 1) and a verifier that canonicalizes the count as that serializer does wrongly accepts, and four credentials whose `behavioralProfile` was changed after signing, which [`core.md`](../core.md) §1.3a.2 rule 1 makes a signature failure because a present profile is well formed only as an object of exactly `checksum`, `generatedAt` and `observationDays`, each of the type the rule gives it: two signed with the baseline credential's profile, one carrying `observationDays` under the name `OBSERVATIONDAYS`, which a verifier that matches member names without regard to case wrongly accepts, and one carrying a fourth member, `riskLevel`, which a verifier that decodes only the three members wrongly accepts, and two signed with no profile, one carrying a profile whose `observationDays` is the JSON string `"14"` and one carrying the JSON string `"sha256:ghi789"` as its profile, which a verifier that projects a profile it cannot decode to the absent form (JSON `null`) wrongly accepts) — each pinned by SHA-256 in `MANIFEST.sha256`, plus two reference verifiers that each verify both declared signature suites: Go (via Cloudflare CIRCL) and Python (via `dilithium-py`, FIPS 204). Both verifiers report 41 of 41 PASS against the shipped fixture set, and the suite's `jcs-vectors/` gate pins the cross-language `JCS(TBS)` byte agreement that [`core.md`](../core.md) §1.3a.3 makes mandatory. Conformance targets (credential, issuer, verifier) are defined in [`core.md`](../core.md) §12. The credential wire shape is additionally published as a machine-readable JSON Schema at [`schemas/atx-credential-v1.1.schema.json`](../schemas/atx-credential-v1.1.schema.json), CI-validated against the §1.1 example here. The conformance suite validates its fixtures against a copy of the schema that it vendors from a pinned revision of this repository, and [`core.md`](../core.md) §12 says which suite fixtures the schema refuses.
